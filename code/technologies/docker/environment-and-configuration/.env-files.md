# 📄 02 - .env Files

> 🌱 **CONCEPTO FUNDAMENTAL:** Los archivos **`.env`** se utilizan para almacenar variables de configuración en un formato sencillo de texto.
>
> Son muy comunes en aplicaciones **Node.js, Angular, Docker y Docker Compose** porque permiten separar la **configuración del proyecto** del código fuente.

# 🌱 ¿Qué es un `.env`?

Un `.env` es un archivo de texto que contiene variables de entorno en formato:

```env
VARIABLE=valor
```

Por ejemplo:

```env
NODE_ENV=development
PORT=3000
DATABASE_URL=postgres://user:password@localhost:5432/mydb
```

Conceptualmente:

```text
.env
 │
 ├── NODE_ENV
 ├── PORT
 └── DATABASE_URL
        ↓
Environment Variables
        ↓
Application
```

> 💡 **IMPORTANTE:** El archivo `.env` **no es una variable de entorno por sí mismo**. Es simplemente una forma práctica de **definir y almacenar valores que después pueden cargarse como variables de entorno**.

---

# 📝 Sintaxis

La sintaxis básica es:

```env
NAME=value
```

Por ejemplo:

```env
NODE_ENV=development
PORT=3000
API_URL=http://localhost:3000
```

También puedes utilizar comentarios:

```env
# Application
NODE_ENV=development
PORT=3000

# Database
DATABASE_URL=postgres://localhost:5432/mydb
```

> 💡 Normalmente cada variable ocupa una línea.

---

# 🧩 ¿Cómo se cargan las variables?

El `.env` por sí solo **no hace que cualquier aplicación pueda leer automáticamente las variables**.

La herramienta o framework que estés utilizando debe cargarlo.

Por ejemplo, una aplicación Node.js puede utilizar una librería como `dotenv`:

```text
.env
  ↓
dotenv
  ↓
process.env
  ↓
Application
```

Entonces:

```env
PORT=3000
```

puede terminar disponible como:

```javascript
process.env.PORT
```

> 🧠 **IDEA CLAVE:** `.env` es una fuente de configuración; las **Environment Variables** son los valores disponibles en el entorno de ejecución.

---

# 🆚 `.env` vs Environment Variables

No son exactamente lo mismo.

| `.env`            | Environment Variables                   |
| ----------------- | --------------------------------------- |
| Es un **archivo** | Son variables disponibles en el entorno |
| Contiene valores  | Son valores disponibles para el proceso |
| `.env`            | `PORT=3000`                             |

Conceptualmente:

```text
.env
   ↓
Carga / configuración
   ↓
Environment Variables
   ↓
Application
```

Por eso puedes tener Environment Variables **sin utilizar ningún `.env`**.

Por ejemplo, Docker puede recibirlas directamente:

```bash
docker run -e PORT=3000 my-api
```

Aquí no necesitas un `.env`.

---

# 🐳 `.env` + Docker

Puedes utilizar un `.env` para proporcionar variables a un container.

Por ejemplo:

```env
NODE_ENV=production
PORT=3000
DATABASE_URL=postgres://...
```

Y utilizarlo con:

```bash
docker run --env-file .env my-api
```

El flujo sería:

```text
.env
  ↓
--env-file
  ↓
Docker
  ↓
Container
  ↓
Environment Variables
  ↓
Application
```

---

# 🧩 `.env` + Docker Compose

Docker Compose utiliza `.env` de diferentes maneras según el caso.

Una de las más comunes es utilizar variables del `.env` para configurar el archivo `compose.yaml`.

Por ejemplo:

```env
POSTGRES_USER=admin
POSTGRES_PASSWORD=password
POSTGRES_DB=myapp
```

Y:

```yaml
services:
  postgres:
    image: postgres:17
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
```

Entonces:

```text
.env
 │
 ├── POSTGRES_USER
 ├── POSTGRES_PASSWORD
 └── POSTGRES_DB
          ↓
     Docker Compose
          ↓
      PostgreSQL
```

> 💡 Esto permite cambiar la configuración sin modificar directamente el `compose.yaml`.

---

# 🔄 Development vs Production

Puedes tener diferentes configuraciones dependiendo del entorno.

### 🧪 Development

```env
NODE_ENV=development
PORT=3000
DATABASE_URL=postgres://localhost:5432/myapp_dev
```

### 🚀 Production

```env
NODE_ENV=production
PORT=3000
DATABASE_URL=postgres://production-db:5432/myapp
```

La aplicación puede ser la misma:

```text
my-api
  │
  ├── Development
  │      ↓
  │   Configuración A
  │
  └── Production
         ↓
      Configuración B
```

---

# 📄 `.env.example`

Aquí aparece una práctica muy importante.

Puedes crear:

```text
.env.example
```

para documentar **qué variables necesita el proyecto**, pero sin incluir valores sensibles reales.

Por ejemplo:

```env
NODE_ENV=development
PORT=3000
DATABASE_URL=
JWT_SECRET=
API_KEY=
```

El flujo para otro desarrollador sería:

```text
.env.example
      ↓
Copiar
      ↓
.env
      ↓
Agregar valores reales
```

Por ejemplo:

```bash
cp .env.example .env
```

Después cada desarrollador configura sus propios valores.

---

# 🔐 `.env` vs `.env.example`

| Archivo        | Contenido                          | ¿Subir al repositorio? |
| -------------- | ---------------------------------- | :--------------------: |
| `.env`         | Valores reales/locales             |    ❌ Normalmente no    |
| `.env.example` | Variables necesarias, sin secretos |          ✅ Sí          |

Por ejemplo:

### `.env`

```env
DATABASE_URL=postgres://admin:super-secret-password@db:5432/app
JWT_SECRET=abc123-super-secret
```

❌ No debería subirse.

Mientras:

### `.env.example`

```env
DATABASE_URL=
JWT_SECRET=
```

✅ Sí puede formar parte del repositorio.

---

# 🚫 `.env` y Git

Uno de los errores más comunes es subir accidentalmente:

```text
.env
```

a GitHub.

Por eso normalmente se agrega al:

```text
.gitignore
```

Por ejemplo:

```gitignore
.env
.env.*
!.env.example
```

Esto significa conceptualmente:

```text
.env
  ↓
.gitignore
  ↓
❌ Git
```

mientras:

```text
.env.example
  ↓
Git
  ↓
✅ Repository
```

---

# ⚠️ ¿Qué NO debería contener un repositorio?

No deberías subir valores reales como:

```text
❌ Database passwords
❌ JWT secrets
❌ API keys privadas
❌ Access tokens
❌ Private credentials
❌ Cloud service credentials
```

Por ejemplo:

```env
DATABASE_PASSWORD=super-secret-password
JWT_SECRET=my-real-secret
API_KEY=my-real-private-key
```

No deberían terminar en:

```text
GitHub
```

---

# 🔥 ¿Y si ya subí un `.env`?

Agregarlo después a `.gitignore` **no elimina automáticamente el archivo del historial de Git**.

Por ejemplo:

```text
.env
  ↓
git add
  ↓
git commit
  ↓
GitHub
```

Después:

```text
.gitignore
  ↓
.env
```

Esto evita futuros commits, pero el secreto puede seguir existiendo en el historial.

> 🚨 **IMPORTANTE:** Si un secreto real fue expuesto, debes considerarlo comprometido y **rotarlo/revocarlo** cuando corresponda.

---

# 🐳 `.env` no es un sistema de Secrets

Esto es muy importante.

Un `.env` es principalmente una forma cómoda de manejar configuración.

> ⚠️ No debes pensar:
>
> `.env` = sistema seguro de secrets.

Por ejemplo:

```text
.env
   ↓
JWT_SECRET=...
```

no convierte mágicamente ese secreto en seguro.

Debes considerar:

* Dónde se almacena el archivo.
* Quién puede acceder a él.
* Si se copia al build context.
* Si termina dentro de una Image.
* Si se expone en logs.
* Si se sube a Git.

Para entornos más avanzados existen mecanismos específicos para manejar secrets.

---

# 🐳 `.env` + Dockerfile

Hay una diferencia importante entre:

```dockerfile
ENV NODE_ENV=production
```

y utilizar:

```text
.env
```

El `Dockerfile` forma parte del proceso de construcción de la Image.

```text
Dockerfile
    ↓
docker build
    ↓
Image
```

Mientras que un `.env` normalmente se utiliza para proporcionar configuración al entorno donde se ejecuta la aplicación:

```text
.env
    ↓
Container
    ↓
Application
```

> ⚠️ Por eso debes evitar copiar innecesariamente un `.env` dentro de una Image:

```dockerfile
COPY . .
```

si el `.env` no está excluido mediante `.dockerignore`.

---

# 🛡️ `.gitignore` vs `.dockerignore`

Son archivos diferentes y protegen contextos diferentes.

| Archivo         | ¿Qué controla?                             |
| --------------- | ------------------------------------------ |
| `.gitignore`    | Qué archivos Git debería ignorar           |
| `.dockerignore` | Qué archivos se excluyen del Build Context |

### `.gitignore`

```text
Project
   ↓
.gitignore
   ↓
Git
```

### `.dockerignore`

```text
Project
   ↓
.dockerignore
   ↓
Docker Build Context
```

Por ejemplo, puedes tener:

```text
.env
```

en ambos:

```text
.gitignore
.dockerignore
```

porque quieres evitar tanto:

```text
.env
   ↓
❌ Git
```

como:

```text
.env
   ↓
❌ Docker Build Context
```

# 🧠 Flujo completo

Una aplicación puede utilizar un `.env` de esta manera:

```text
              .env
                │
                ▼
        Configuration values
                │
                ▼
      Environment Variables
                │
                ▼
            Container
                │
                ▼
           Application
```

Con Docker:

```text
.env
 │
 ▼
--env-file
 │
 ▼
Container
 │
 ▼
process.env
```

Y con Docker Compose:

```text
.env
 │
 ▼
Docker Compose
 │
 ▼
Services
 │
 ├── API
 ├── PostgreSQL
 └── Redis
```

---

# 🔥 La idea que debes conservar

Piensa en `.env` como **un archivo de configuración**, no como la aplicación ni como un sistema de seguridad.

```text
.env
   ↓
Configuración
   ↓
Environment Variables
   ↓
Application
```

Y recuerda estas tres reglas:

| Archivo        | Regla                                 |
| -------------- | ------------------------------------- |
| `.env`         | ❌ No subir secretos reales a GitHub   |
| `.env.example` | ✅ Documentar las variables necesarias |
| `.gitignore`   | ✅ Evitar que `.env` termine en Git    |

> 💡 **IDEA PRINCIPAL:** El código debe saber qué configuración necesita, pero los valores concretos de esa configuración deberían poder proporcionarse desde el entorno en el que la aplicación se ejecuta.
