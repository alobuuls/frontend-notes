## 🐳 ¿QUÉ ES `.dockerignore`?

`.dockerignore` es un archivo de texto utilizado por Docker para indicar qué archivos y directorios deben **excluirse del Build Context**.

Por ejemplo:

```dockerignore
node_modules
.git
.env
dist
coverage
npm-debug.log
```

Cuando ejecutas:

```bash
docker build -t my-api:1.0 .
```

Docker toma `.` como **Build Context** y aplica las reglas de `.dockerignore` antes de procesarlo.

```text
Project
    ↓
.dockerignore
    ↓
Archivos excluidos
    ↓
Build Context
    ↓
docker build
```

> 💡 **Idea clave:** `.dockerignore` funciona como un **filtro del Build Context**.

---

## 📦 ¿POR QUÉ EXISTE?

Imagina un proyecto así:

```text
my-api/
├── src/
├── node_modules/
├── .git/
├── .env
├── dist/
├── coverage/
├── package.json
├── package-lock.json
├── Dockerfile
└── .dockerignore
```

No necesitas enviar todo eso al Build Context.

Por ejemplo:

```text
node_modules/
.git/
coverage/
dist/
.env
```

pueden ser innecesarios para construir la Image.

`.dockerignore` permite excluirlos.

---

## ⚡ REDUCIR EL BUILD CONTEXT

Una de sus funciones principales es reducir la cantidad de archivos que Docker necesita procesar.

### ❌ Sin `.dockerignore`

```text
Proyecto
   ↓
Muchísimos archivos
   ↓
Build Context grande
   ↓
docker build
```

### ✅ Con `.dockerignore`

```text
Proyecto
   ↓
.dockerignore
   ↓
Archivos innecesarios excluidos
   ↓
Build Context pequeño
   ↓
docker build
```

Esto puede ayudar a:

* ⚡ acelerar el build
* 📦 reducir el tamaño del contexto
* 🧹 evitar archivos innecesarios
* 🔧 hacer los builds más eficientes

## 📁 `node_modules`

Un caso muy común en proyectos Node.js:

```dockerignore
node_modules
```

¿Por qué?

Porque normalmente las dependencias se instalan **dentro de la Docker Image**:

```text
package.json
      ↓
Dockerfile
      ↓
npm install
      ↓
node_modules
      ↓
Docker Image
```

No necesitas enviar tu `node_modules` local.

Además, puede contener dependencias instaladas para un sistema operativo diferente al del container.

Por ejemplo:

```text
Windows
   ↓
node_modules local
```

no necesariamente es lo que quieres utilizar dentro de:

```text
Linux Container
   ↓
npm install
   ↓
Linux dependencies
```

---

## 🌿 `.git`

También suele excluirse:

```dockerignore
.git
```

Tu historial de Git normalmente no es necesario para ejecutar la aplicación.

No necesitas enviar:

```text
.git/
   ├── commits
   ├── branches
   ├── objects
   └── history
```

al Build Context.

---

## 📊 Archivos generados

También puedes excluir archivos generados que no necesites:

```dockerignore
dist
coverage
```

Por ejemplo:

```text
coverage/
```

contiene resultados de testing que normalmente no necesitas dentro de la Image.

> ⚠️ En algunos proyectos `dist/` sí puede ser necesario, dependiendo de la estrategia de build, así que **no debes excluirlo automáticamente sin entender tu Dockerfile**.

---

## 🔐 `.env` Y ARCHIVOS SENSIBLES

Puedes encontrar reglas como:

```dockerignore
.env
.env.*
```

Esto evita que esos archivos entren al Build Context.

Por ejemplo:

```text
.env
    ↓
.dockerignore
    ↓
❌ Excluido
```

Pero aquí hay algo **MUY importante**:

> 🚨 `.dockerignore` **no es un sistema de gestión de secrets**.

Su función es controlar qué archivos forman parte del Build Context.

No debes pensar:

```text
.dockerignore
      ↓
"mis secrets están seguros"
```

❌ No funciona así.

La gestión correcta de secretos debe hacerse mediante mecanismos apropiados de secrets/configuración, no simplemente ocultando un archivo con `.dockerignore`.

## 🧩 RELACIÓN ENTRE `COPY` Y `.dockerignore`

Esto es especialmente importante.

Supongamos:

```text
my-api/
├── src/
├── .env
├── package.json
├── Dockerfile
└── .dockerignore
```

Y:

```dockerignore
.env
```

Luego tu Dockerfile tiene:

```dockerfile
COPY . .
```

Podrías pensar:

> 💭 "¿No va a copiar `.env` porque hice `COPY . .`?"

No.

El **Build Context ya fue filtrado mediante `.dockerignore`**.

```text
Project
   │
   ├── src/         ✅
   ├── package.json ✅
   ├── Dockerfile   ✅
   └── .env         ❌
          ↓
    .dockerignore
          ↓
    Build Context
          ↓
       COPY . .
          ↓
      Docker Image
```

Por eso `.dockerignore` afecta a los archivos que Docker puede utilizar desde el contexto.

## 🏗️ `.dockerignore` Y BUILD CONTEXT

Recuerda el flujo completo:

```text
Project
   │
   ├── Dockerfile
   ├── src/
   ├── package.json
   ├── node_modules/
   ├── .git/
   └── .env
          │
          ▼
    .dockerignore
          │
          ├── ❌ node_modules
          ├── ❌ .git
          └── ❌ .env
          │
          ▼
    Build Context
          │
          ▼
      docker build
          │
          ▼
       Image
```

### 📁 Proyecto

```text
my-api/
├── src/
│   ├── app.js
│   └── server.js
├── node_modules/
├── .git/
├── .env
├── coverage/
├── package.json
├── package-lock.json
├── Dockerfile
└── .dockerignore
```

### 📄 `.dockerignore`

```dockerignore
node_modules
.git
.env
coverage
```

Entonces:

```text
Proyecto original
      ↓
.dockerignore
      ↓
┌─────────────────────┐
│ src/                │
│ package.json        │
│ package-lock.json   │
│ Dockerfile          │
└─────────────────────┘
      ↓
Build Context
      ↓
docker build
```

Los archivos excluidos **no forman parte del contexto disponible para el build**.

---

## ⚠️ `.dockerignore` NO ES LO MISMO QUE `.gitignore`

Pueden parecer similares porque ambos excluyen archivos, pero tienen propósitos diferentes:

| `.gitignore`                     | `.dockerignore`                         |
| -------------------------------- | --------------------------------------- |
| Controla qué archivos ignora Git | Controla qué archivos excluye Docker    |
| Afecta Git                       | Afecta Docker Build Context             |
| Evita archivos en el repositorio | Evita archivos en el contexto del build |
| Se utiliza con Git               | Se utiliza con Docker                   |

Puedes tener:

```text
.gitignore
.dockerignore
```

al mismo tiempo.

Y **no necesariamente deben contener exactamente las mismas reglas**.

---

## 📋 `.dockerignore` COMÚN EN NODE.JS

Un ejemplo típico podría ser:

```dockerignore
node_modules
.git
.env
.env.*
coverage
npm-debug.log*
Dockerfile*
docker-compose*
```

> ⚠️ Pero no debes copiar esta lista automáticamente.

Lo correcto es preguntarte:

> **¿Qué archivos necesita realmente mi Dockerfile para construir la Image?**

Todo lo demás que no deba formar parte del Build Context puede evaluarse para exclusión.

---

## 🧠 LA IDEA MÁS IMPORTANTE

Piensa en `.dockerignore` como un **filtro del Build Context**:

```text
                 PROJECT
                    │
                    ▼
             .dockerignore
                    │
          ┌─────────┴─────────┐
          │                   │
     Archivos útiles     Archivos excluidos
          │                   │
          ▼                   ✕
      BUILD CONTEXT
          │
          ▼
      docker build
          │
          ▼
        IMAGE
```

Y recuerda esta relación:

```text
.dockerignore
      ↓
Build Context
      ↓
COPY
      ↓
Dockerfile
      ↓
Docker Image
```

> 🎯 **En resumen:** `.dockerignore` no construye la Image ni controla directamente qué queda dentro de ella; principalmente determina qué archivos Docker recibe como contexto para realizar el build.
